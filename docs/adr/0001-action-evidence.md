# ADR 0001. Журнал доказательств и подпись в режиме GitHub Action

Статус: **принято** (этап 3). Место в репозитории: `docs/adr/0001-action-evidence.md`.

## Контекст

Gatekeeper в режиме Action работает в CI клиента: код не покидает его инфраструктуру. Каждая проверка превращается в подписанную аттестацию (Trust Core: in-toto `test-result` в конверте DSSE) и добавляется в журнал RFC 6962 с чекпоинтами C2SP. Нужно решить, где живёт журнал и чем подписываются записи.

Ограничение, определившее выбор: встроенные attestations GitHub (`actions/attest`, keyless через Sigstore) в частных репозиториях доступны только на тарифе Enterprise Cloud, а у частного экземпляра Sigstore GitHub нет журнала прозрачности. Целевые клиенты — частные репозитории на тарифе Team.

## Решение A. Журнал — ветка `gatekeeper-evidence` в репозитории клиента

- Сиротская ветка (без общей истории с кодом), в корне — каталог журнала `filelog` (`checkpoint` + `entries/`).
- **Origin журнала:** `github.com/<owner>/<repo>/gatekeeper-evidence/v1`. Суффикс `/v1` — версия формата журнала.
- Запись — только при `push` в ветку по умолчанию. Запуски на PR ничего не пишут.
- **Параллельные запуски:** без `concurrency`-группы (см. поправку 2), оптимистичная запись с повтором:
  `fetch → reset на origin/gatekeeper-evidence → append заново → push`, до 5 попыток с нарастающей паузой и случайным разбросом. После 5 неудач задание падает явно.
- **Идемпотентность:** запись с тем же `run_id` и `run_attempt` повторно не добавляется. Перезапуск задания не создаёт дубликатов.
- **Ruleset для ветки `gatekeeper-evidence`:** запрет удаления и force push. PR для этой ветки **не** требуется, иначе задание не сможет писать.
- **Гарантия — не ruleset, а копии чекпоинтов у других сторон** (см. поправку 3).

## Решение B. Подпись — ключ Ed25519 в секрете окружения

- Environment `gatekeeper-evidence`, разрешённая ветка развёртывания — только ветка по умолчанию. Секрет `GATEKEEPER_SIGNING_KEY` (PEM, PKCS#8).
- Один ключ подписывает и конверт записи, и чекпоинт (в режиме Action оператор журнала и аттестатор — одна сторона, клиент). Ротация — эпохами, см. ADR 0002 в trust-core (`trust-core/docs/adr/0002-key-rotation.md`).
- Публичный ключ лежит в `.gatekeeper/evidence.pub` в ветке по умолчанию. **Аудитор получает ключ от клиента напрямую**, а файл в репозитории использует только для сверки.
- **Этап 6:** независимая контрподпись через OIDC. Ваш сервис проверяет токен GitHub Actions (`iss`, `aud`, `sub`, `repository`, `ref`, `sha`, `run_id`) и подписывает как свидетель. Платная функция open-core.
- **Опционально:** для публичных репозиториев и клиентов на Enterprise Cloud — `actions/attest` как вторая, независимая подпись.

### Обязательный чек-лист задания `record`

Расширенный чек-лист — `docs/adr/0003-distribution.md`, раздел «Чек-лист
задания `record` у клиента» (composite action, ключ только в `env`
последнего шага, никакой сборки в этом задании).

Задание, которому доступен ключ:
1. Запускается только при `push` в ветку по умолчанию: `if: github.event_name == 'push' && github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`.
2. `environment: gatekeeper-evidence`, `permissions: contents: write` и больше ничего. `id-token: write` появится только на этапе 6.
3. Все actions закреплены на полных SHA. Разрешены только `actions/checkout`, `actions/setup-go`, `actions/download-artifact`.
4. Никаких `npm install`, `pip install`, `curl | sh`, сторонних скриптов, `submodules`.
5. Бинарник собирается из исходников этого репозитория с `GOFLAGS=-mod=readonly` (зависимости проверяются по `go.sum`).
6. Ключ передаётся только через переменную окружения и не пишется на диск.
7. Во всём репозитории нет триггеров `workflow_run` и `pull_request_target`. Проверяется в CI.

## Модель угроз (формулировка для документации и статей)

> Подпись удостоверяет, что владелец ключа заявил этот результат для этого коммита с этой версией сканера и правил, и что заявление не изменено задним числом — при условии, что копии чекпоинтов хранятся вне репозитория. Правдивость заявления проверяется воспроизведением: сканер детерминирован, а в аттестации закреплено всё, что нужно для повтора. Подпись не удостоверяет, что сам запуск не сфабрикован владельцем ключа; независимое подтверждение запуска — OIDC-свидетель на этапе 6.

### Что закреплено в аттестации для воспроизведения

- subject: `git+https://github.com/<owner>/<repo>` + `gitCommit: <sha>` — откуда взять артефакт;
- configuration: `sha256` встроенных правил gitleaks, версия gitleaks, версия gatekeeper;
- аннотация `reproduce`: точная команда повтора;
- `url`: ссылка на запуск CI; аннотации `run_id` и `run_attempt`.

Воспроизведение: checkout коммита → `gatekeeper scan` той же версии → побайтно тот же `result.json`.

## Поправки к отзывам на решения

1. **Версия — не в теле чекпоинта.** Формат чекпоинта — стандарт C2SP. Добавленное поле сломает совместимость со свидетелями и Tessera. Версия уже есть там, где её место: в origin журнала (`…/v1`), в `_type` аттестации (`Statement/v1`), в `predicateType` (`test-result/v0.1`) и в `payloadType` конверта.
2. **`concurrency`-группа опасна для журнала.** GitHub отменяет ожидающий запуск в группе, когда встаёт в очередь следующий. При трёх быстрых push средний коммит остался бы без записи. Поэтому запись оптимистичная, с повтором.
3. **Повтор — это append заново, а не `git rebase`.** Файл `checkpoint` меняется при каждой записи, rebase будет конфликтовать на нём всегда. Правильно: сбросить рабочую копию на удалённую ветку и добавить запись поверх.
4. **Summary запуска — не гарантия.** Администратор репозитория может удалить запуски и их логи. Гарантию дают только копии чекпоинтов у других сторон: аудитор (`trustcore verify -previous`), на этапе 6 — свидетель.
5. **Миграция на Tessera не ломает старые чекпоинты.** Хэширование RFC 6962 одинаково, поэтому воспроизведение тех же записей в Tessera даёт те же корни, и старые чекпоинты проверяются как префиксы. Путь миграции — перенос записей по порядку с проверкой корня на каждом старом чекпоинте.
6. **Рост журнала.** Сейчас каждая запись пересчитывает корень за O(n) и перечитывает все записи. Порог миграции — техническая метрика, а не дата: когда время `record` превысит 10 секунд. Промежуточный шаг без смены формата — хранить хэши листьев или компактный диапазон RFC 6962 (O(log n) на запись).

## Отвергнуто

- Артефакты workflow: удаляются по сроку хранения; в задании с ключом не используются, чтобы оно оставалось минимальным. Копии чекпоинта — история ветки журнала, summary запуска и, главное, копии у аудитора.
- Отдельный репозиторий доказательств: нужен межрепозиторный токен — ещё один секрет. **В плане:** вариант для организаций с десятками репозиториев.
- Keyless через публичный Sigstore из частного репозитория: имя репозитория попадает в сертификат и публичный журнал Rekor.
- `concurrency`-группа: см. поправку 2.
