# ADR 0003. Форма распространения Gatekeeper для клиентов

Статус: **принято** (редакция 2, после двух ревью). Место: `devsecops-gatekeeper/docs/adr/0003-distribution.md`.

## Контекст

`gatekeeper.yml` собирает `gatekeeper` из исходников **этого же** репозитория, поэтому подключить Gatekeeper к другому репозиторию (`trust-core`, клиент) нельзя. Это блокирует этап 4.4, Marketplace (этап 5) и любых клиентов.

Требования (унаследованы из принятых решений):
1. **Marketplace** — первый двигатель входящего потока. Публикуются только action: один `action.yml` в корне публичного репозитория; action из подпапок и переиспользуемые workflow не публикуются; первая публикация — вручную, с принятием соглашения; описание ≤ 125 символов.
2. **Задание с ключом минимально** (ADR 0001).
3. **Клиент видит, что у него выполняется.**
4. **Нулевая инфраструктура** на старте.
5. **Клиенты — частные репозитории на тарифе Team** (без функций Enterprise).

## Варианты

| | A. Переиспользуемый workflow | B. Composite action, сборка из исходников | C. Composite action, бинарники с provenance | D. Docker-action |
|---|---|---|---|---|
| Marketplace | **нет** | да | да | да |
| Что выполняется | наш workflow | исходники по закреплённому SHA, зависимости по `go.sum` | бинарник, сверенный по SHA-256 из `action.yml` | образ по digest |
| Прозрачность | высокая | **максимальная** | через `gh attestation verify` | через проверку образа |
| Инфраструктура у нас | нет | нет | релизы, attestations в нашем публичном репозитории | реестр, сборка образа |
| Раннеры | любые | любые с Go | по бинарнику на платформу | только Linux |

**A отвергнут** — не публикуется в Marketplace. **D отвергнут** — реестр и только Linux без выигрыша над C. JavaScript-action не рассматривался: для Go-инструмента это обёртка над скачиванием бинарника, то есть C плюс среда Node.

## Решение: composite action в корне репозитория; v1 — B, v2 — C по сигналу

### Ключевая поправка ревью: ключ и сборка разделены по заданиям
Переменная `env`, заданная на шаге `uses:`, видна **всем внутренним шагам** composite action. Если собирать бинарник в задании с ключом, ключ находится в окружении во время установки Go, загрузки модулей и компиляции: вредоносная зависимость с кодом в `init()` теоретически может его прочитать. Поэтому:

- **Сборка — только в задании `scan`** (без секретов): бинарник собирается из `github.action_path` по закреплённому SHA (`-trimpath`, `GOFLAGS=-mod=readonly`, встроенный кэш `actions/setup-go` по `go.sum` action) и передаётся в `record` артефактом вместе с `result.json`.
- **В задании `record` нет Go, загрузки модулей и компиляции.**
- **Checkout ветки журнала делает шаблон клиента** в отдельный `path: evidence` **до** шага с ключом — никакого перезаписывания рабочего каталога и никакого стороннего action в окружении ключа.
- **Ключ — только в `env` последнего шага** (`uses: XtReL/devsecops-gatekeeper@<SHA>` с `mode: record`). Внутри этого шага выполняются только наш бинарник и наш скрипт.

### Режимы action
- `mode: build` — установка Go и сборка; выход — путь к бинарнику.
- `mode: scan` — `gatekeeper scan`; выходы — путь к `result.json` и код.
- `mode: target` — `gatekeeper evidence-target`; выходы — `branch`, `origin` (без ключа).
- `mode: record` — `evidence-push.sh` с уже собранным бинарником; ключ **только** из `env` (`GATEKEEPER_SIGNING_KEY`), никогда из `inputs`: значения входов подставляются в скрипты через `${{ inputs.… }}` — путь к инъекции в shell; `env` исключает подстановку и ограничен одним шагом.

### Шаблон workflow клиента
- `scan` (PR и push, без секретов): checkout → `mode: build` → `mode: scan` → `upload-artifact` (`result.json` и бинарник).
- `record` (только push в ветку по умолчанию, `environment: gatekeeper-evidence`, `contents: write`): checkout кода (для `.gatekeeper/evidence.json`) → `download-artifact` → `mode: target` → `actions/checkout` ветки журнала в `path: evidence` → `mode: record` с ключом в `env`.
- Оба задания — на одной ОС раннера (бинарник собирается под неё).

### v2 — C, по измеримому сигналу
Переход, когда выполнено хотя бы одно:
- p95 времени шага `build` > 60 с;
- ≥ 1 падения из-за сборки на 100 запусков;
- > 10 подключённых репозиториев.

Тогда: релизный workflow собирает бинарники под платформы с attestations сборки (публичный репозиторий — публичный Sigstore и Rekor; клиенту Enterprise не нужен); `action.yml` закрепляет SHA-256 каждого бинарника; `mode: build` заменяется скачиванием и сверкой. Интерфейс остальных режимов не меняется.

## Чек-лист задания `record` у клиента (расширяет ADR 0001)
1. Только push в ветку по умолчанию; `environment: gatekeeper-evidence`; `permissions: contents: write`.
2. Разрешены только `actions/checkout`, `actions/download-artifact` и `XtReL/devsecops-gatekeeper@<полный SHA>`.
3. Ключ — только в `env` шага `mode: record`; никакой сборки в этом задании.
4. Никаких `workflow_run` и `pull_request_target`.

## Размещение
- Action — в корне **`devsecops-gatekeeper`**: здесь уже живут журнал доказательств, environment, ключ и ruleset; перенос action означал бы новый журнал с нуля. Репозиторий уже публичный — новой публичности нет.
- **Облачный режим** (`cmd/api`, `cmd/scanner`, связанные `internal/…`, `docker-compose`, `k8s`) переносится в отдельный **закрытый** репозиторий, когда его понадобится закрыть — это совпадает с планом open-core (`gatekeeper-cloud` закрыт). Закрывать нужно облачный код, а не action: Marketplace требует публичности репозитория action.

## Dogfooding
- `devsecops-gatekeeper` переходит на свой action через `uses: ./` — каждый PR проверяет сам action.
- `trust-core` подключает `XtReL/devsecops-gatekeeper@<SHA>` со своим журналом, environment и ключом (этап 4.4).

## Сопутствующее
- `docs/onboarding.md` — подключение клиента: ключ на устройстве, environment, секрет, `evidence-init`, ruleset, шаблон workflow, первая проверка `trustcore verify`.
- Для Marketplace (этап 5): уникальное имя, описание ≤ 125 символов, `branding` задаём всегда.

## Допущения, проверяемые первым прогоном
- Вызов `actions/setup-go` изнутри composite action и работа встроенного кэша по пути action.
- Время шага `build` — замерить сразу: это исходные данные для сигнала перехода на C.
