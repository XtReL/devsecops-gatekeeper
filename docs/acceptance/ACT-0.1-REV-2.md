## 1. Авторство (поправка a)

В REV-1 написано, что ревизию подготовил Claude Sonnet 5.5. Это ошибка задания.

| Работа | Кто | Источник |
|---|---|---|
| Акт ACT-0.1 | Claude Opus 5.5, сессия Claude Code | трейлер коммита `71c9284`: `Co-Authored-By: Claude Opus 5.5`, `Claude-Session: https://claude.ai/code/session_01BuLv7GWSSECmmYHuPSq3sV` |
| Раскладка способов и поправки к акту (текст REV-1) | Claude Opus 5.5, чат claude.ai | слова владельца. В репозитории это не подтверждается |
| Запись файла REV-1 и сверка раскладки с колонкой «Как проверено» | сессия Claude Code | трейлер коммита `e681b44`: `Co-Authored-By: Claude Sonnet 5.5`, та же ссылка на сессию |
| Запись REV-2 и исходников контролей | та же сессия Claude Code | трейлер коммита REV-2 |

Модель этой сессии по факту. Данные `get_session`, вызван при подготовке REV-2:

- `configured_model`: `claude-opus-5-5`;
- `session_context.model`: `claude-sonnet-5-5`;
- `external_metadata.last_served_model`: `claude-sonnet-5-5`;
- `external_metadata.user_switched_model`: `claude-sonnet-5-5`;
- `origin`: `web_claude_ai`.

Значит, сессия была создана с Opus 5.5, потом модель переключил пользователь, и сейчас её обслуживает Sonnet 5.5. `get_session` хранит только текущее состояние, а не модель по ходам. Для REV-1 доказательств нет, кроме трейлера коммита и слов системного сообщения того хода: оба называют Sonnet 5.5.

Точная формулировка для шапки REV-1: «Раскладку способов и поправки подготовил Claude Opus 5.5 в чате claude.ai. Файл записала сессия Claude Code, которую при записи обслуживал Claude Sonnet 5.5».

Независимость, по данным владельца:

- Раскладку и поправки готовил Claude Opus 5.5, акт составил тоже Claude Opus 5.5, но в другой сессии. Это уровень 2: та же модель, другая сессия.
- Сверку раскладки с колонкой «Как проверено» акта делала сессия Claude Code. Это та же сессия, что составила акт (одинаковая ссылка `Claude-Session`). Контекст сессии общий, модель переключена пользователем. Независимость сверки от акта по этому признаку ниже, чем у раскладки. Уровень для неё здесь не назначается.

## 4. C4, основание (поправка d)

В задании REV-1 пункты 2g и 5 противоречили друг другу: основание нужно записать, а подробности про приложение и туннель писать нельзя. Это ошибка задания. REV-1 разрешил противоречие в пользу краткости. В REV-2 принято такое правило: факты пишем, адреса и имена не пишем.

Основание статуса О для C4 (наблюдение):

- 2026-10-10 в 16:47 UTC две доставки вебхука GitHub App получили от туннельного сервиса ответ 404 с ошибкой «endpoint offline».
- Приложение установлено только на аккаунте владельца.

Что это показывает: в этот день вход облачного режима (вебхук GitHub) был недоступен. Это не доказывает, что код не может работать. Чтение кода в акте (нет пути выдачи прав на настоящий репозиторий) этому не противоречит.

Статус действует на 2026-10-10. После отключения вебхука облачная часть не получает событий. Если вебхук включат снова или систему развернут, C4 нужно проверять заново.

### Расхождения и уточнения при сверке

1. **Девять облачных файлов.** Число 9 файлов и +1335 −165 воспроизводится только для одного набора, найденного перебором среди 23 файлов облачных путей: `Dockerfile.scanner`, `cmd/api/main.go`, `cmd/scanner/main.go`, `internal/billing/IMPLEMENTATION_GUIDE.md`, `internal/billing/README.md`, `internal/billing/subscription.go`, `internal/billing/webhook.go`, `internal/billing/webhook_test.go.bak`, `internal/iam/spicedb.go`. Определение «облачных файлов» в задании не дано, поэтому совпадение с этим набором не доказано. Широкий набор облачных путей (`cmd/api`, `cmd/scanner`, `internal/` кроме `engine` и `evidence`, `docker-compose.yml`, `k8s`, `Dockerfile*`, `iam/`) даёт 23 файла, +1780 −199. В девятке три файла не являются кодом (два `.md` и `.bak`). В неё не входят другие изменившиеся файлы кода, например `internal/config/config.go`, `internal/db/database.go`, `internal/broker/nats.go`, `internal/middleware/*.go`. Для вывода о том, насколько образы отличаются от HEAD, надёжнее брать широкий набор, а не девятку.
2. **Ingress.** В `k8s/api-deployment.yaml:96` написано: `type: ClusterIP # Сервис доступен только внутри кластера. Внешний трафик пустим только через Ingress.` Манифеста Ingress в репозитории нет, но комментарий предполагает его вне репозитория. Фраза «в k8s нет Ingress» верна для манифестов. Но она не исключает, что Ingress есть в кластере и что-то делает с заголовками. Допущение п. 2.d остаётся допущением в обе стороны: репозиторий не описывает ни Ingress, ни прокси.
3. **Возраст образов.** В Р2 REV-1 написано «около 4 месяцев назад». От 2026-06-22 до 2026-10-10 прошло 110 дней, это около 3,6 месяца.
4. **Манифесты k8s ссылаются не на опубликованные образы.** В `k8s/api-deployment.yaml:28` и `k8s/scanner-deployment.yaml:27` стоят имена `ghcr.io/your-github-username/devsecops-gatekeeper-...:latest`. Это шаблонное имя, а не путь опубликованных образов.

### Наблюдение при сверке (вне заявлений, не проверялось прогоном)

Пробы k8s идут на `/api/v1/findings?repo=health-check` с `X-User-Login: health-monitor`. В коде на `7e2f7b6` этот обработчик спрашивает SpiceDB о праве `writer` пользователя `health-monitor` на репозиторий `health-check`. Если такое право не выдано, ответ будет 403, а проба считает успехом только коды 200-399. Это вывод по чтению. Какие права есть в SpiceDB в реальной установке, неизвестно. Проверять можно только при развёрнутой системе.
